# P002 — Separate CPU and SoC correctness

**Status:** complete. **Review date:** 2026-10-23. **Branch:** `main`.

**Selected target:** Apple M1 / T8103 / H13G; Mac mini (M1, 2020), board J274.

## Requirement and delivered evidence

The original roadmap requirement is preserved: publish independent definitions for ISA accuracy, Apple CPU profile, peripherals and whole-machine compatibility. Its acceptance condition is that each release gate identifies its fidelity level. P002 implements that definition and verification contract; runtime emulator work remains in the later phases.

| Acceptance item | Delivered evidence |
|---|---|
| Four correctness domains have independent definitions | [P002 architecture contract](../ARCHITECTURE.md#p002-fidelity-contract): each definition states its subject, required evidence and exclusions. |
| Linux and macOS claims remain separate | Separate `machine-linux` and `machine-macos` classifications; no v0.1 gate awards macOS compatibility. |
| Generic smoke and review reports cannot become hardware claims | Separate `toolchain` and `evidence-audit` labels, with explicit limits. The manifest contains requirements and no runtime success fields. |
| All named development and formal release gates identify fidelity | G0–G6 and P361–P365 are classified in [fidelity.json](../fidelity.json) and both architecture tables; the five formal roadmap phases carry matching annotations. |
| Classifications remain bounded | G1 covers only exercised ISA/Apple-profile skeleton behavior; G2 supplies the peripheral evidence also needed by P361. G5 covers only compared device transitions. Linux lab boot, stock Apple firmware, graphics and timing are not conflated. |
| Future drift fails automatically | `tools/validate_fidelity.py` checks the required IDs, fixed mappings, schema and visible definitions/tables/roadmap annotations, with readable diagnostics and `--root` support. |
| Negative cases exercise actual failure paths | `tests/test_fidelity.py` mutates every level/gate, malformed fields, duplicate JSON keys, hidden or duplicated Markdown, omitted formal annotations and attempted generic-smoke promotion. |
| Research has auditable sources | [P002 primary references](../REFERENCES.md#p002-fidelity-evidence), including pinned QEMU, Asahi and Linux snapshots plus reviewed Arm/Apple vendor pages. |
| Enforcement is integrated | CI, README, development instructions and AGENTS include the fidelity validator. All original roadmap descriptions/checks and G0–G6 observable tests are preserved. |

## Build dependency and hosted verification

The unchanged generic ARM64 experiment could not build locally: `make -C experiments/arm64-virt-smoke` exited 2 because `aarch64-linux-gnu-gcc` is unavailable (compiler invocation error 127). `qemu-system-aarch64` is also absent. No local guest-execution result is claimed.

The push-triggered [verification workflow](https://github.com/cheshmakzanoon-ops/M1-apple-Emulator-v0.1/actions/workflows/verify.yml) installs those tools, builds the original guest and runs its `virt` smoke test independently of the metadata job. The check attached to the implementation commit is the hosted result; it must not be confused with an Apple-machine test. P002 changes no guest code or machine model.

## Deviations and limits

No phase-scope deviation. P003–P365 remain unchecked. P003 still owns the reproducible G4 Linux witness specification. The hardware map, target charter, generic smoke payload and existing validators are preserved.

The new validator checks the explicit schema, classifications and published text consistency. It does not prove arbitrary prose true, authenticate remote sources, execute an emulator, compare physical silicon or infer runtime gate completion. Coordinated prose edits still require engineering review. Adding a new gate requires an explicit inventory, classification and test update.

P002 supplies no Apple CPU personality, MMIO device, T8103 machine, Linux boot, macOS support, firmware, graphics or cycle-accuracy implementation. Source snapshots establish the distinctions used in the contract; no physical-hardware experiment was needed or performed.
